# M1 设计：plansql —— plan 式两段生成 pipeline

> 状态：已批准（2026-07-22 与用户商定）。实现于 `model/pipeline/`。
> 参考论文 OraPlan-SQL（`docs/material/2510.23870v1.pdf`），但**不是**照抄复现，
> 取舍见下与 `docs/PROGRESS.md` 决策记录。

## 1. 目标

给 Archer 评测建立"先规划、后写 SQL"的对照组 pipeline（总路线图 M1）：

```
question + schema ──planner LLM──→ plan 文本 × n
plan + question + schema ──sqlgen LLM──→ SQL 候选 × n
候选 ──只读执行──→ 失败淘汰 ──结果多数投票──→ 最终 SQL
```

M2 将在 plan 与 sqlgen 之间插入 DSL 结构化 + 校验阶段，stage 列表就是插槽。

## 2. 与论文的差异（全部为有意取舍）

| 论文 | 本实现 | 原因 |
|---|---|---|
| embedding 检索 top-k schema | 全量 schema + 每表 3 行样本 | Archer 单库表少，检索无益 |
| SQL agent 带 ICL few-shot 检索 | 不加 | 消融仅 +1.93；保持对照组纯净 |
| planner 提示词内嵌 meta-prompting 蒸馏的 guidelines | 通用规划提示词 | guidelines 冲着刷分蒸馏，泛化性存疑 |
| entity-linking 提示词指引 | 默认不加（提示词是文件，可手动加） | 同上 |
| 多 plan（temp 0.7）+ 投票 | 机制照实现，**默认 n_plans=1** | 消融仅 +0.97；先省成本 |
| 无执行修复闭环 | 同论文：失败直接淘汰 | 修复留给 M2 的 DSL 校验环 |
| 中文 direct generation（不翻译） | 同论文 | 附录 5.2：79.8 vs 55.8 |

## 3. 结构

```
model/llm.py                # ChatEndpoint：OpenAI 兼容 chat 封装（从 api.py 抽取，APIModel 共用）
model/pipeline/
├── __init__.py             # PlanSQL(SQLGenerator)：组装 stages、样本级并发、trace；PlanSQLFlash 注册 "plansql-flash"
├── context.py              # PipelineContext / Candidate：单条样本贯穿全程的状态包
├── templates.py            # 提示词模板加载 + 占位符校验（写错变量名 → 报错并列出可用项）
├── stages/
│   ├── plan.py             # PlanStage：→ ctx.plans（n_plans=1 时 temp 0；>1 时 temp 0.7）
│   ├── generate.py         # GenerateStage：每个 plan → 候选 SQL（temp 0，extract_sql 去栅栏）
│   └── vote.py             # VoteStage：execute_sql 只读执行 → 结果规范化分组 → 多数投票
├── prompts/
│   ├── README.md           # 占位符字典与内容流动图
│   ├── planner.system.md   # （无占位符）
│   ├── planner.user.md     # {schema} {question}
│   ├── sqlgen.system.md    # （无占位符）
│   └── sqlgen.user.md      # {schema} {question} {plan}
└── __main__.py             # --preview N：打印实际发给两个 LLM 的完整消息
```

## 4. 关键行为

- **接口不变**：`PlanSQL` 是普通 `SQLGenerator`，`python -m model --model plansql-flash --data en_dev --eval` 直接可用；预测文件仍是纯 SQL 数组。
- **投票口径**：结果按行多重集比较（行序不敏感，浮点按 `config.FLOAT_PRECISION` 归一，
  与评测器同源），最大组获胜，平票取 plan 序号小者。
- **兜底**：全部候选执行失败 → 返回最后一条候选 SQL（不返回空串，便于事后诊断）；
  LLM 调用本身异常 → 按框架约定记空串。
- **trace**：每条样本的 plans / 候选 SQL / 执行错误 / 投票详情落
  `predictions/<模型名>_<数据集>.trace.json`（runner 在写预测文件后顺手写出，
  通过 `generator.trace_records` 钩子，评测器不感知）。
- **参数随模型走**（铁律 #2）：`n_plans` `plan_temperature` 及骨干 endpoint 均为类属性，
  新变体 = 子类 + MODELS 注册一行。

## 5. 测试策略

- 模板加载/占位符校验、投票分组：纯函数单测。
